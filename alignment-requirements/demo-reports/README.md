# Demo reports

One short report per prototype demo, so each new demo can see what the others tried, build on what worked, and try something the others didn't. Think of it as seeing what the other teams in a class project did before starting your own.

| Demo | Direction | Report |
|---|---|---|
| Loupe | A - single screen, three columns | [loupe.md](loupe.md) |
| Passport Control | C - guided, tracked status, one step at a time | [passport.md](passport.md) |
| Quilt | D - triage the whole code system, disease blocks, most common first | [quilt.md](quilt.md) |

## Format

Copy the layout of `loupe.md`:

1. **Header table:** codename, direction, branch/folder, pull request (none for demos built on `prototypes`), how to try it, date built.
2. **What it focused on:** the question it tested, its personality/flair (the concept or theme that makes it memorable), and how the screen works, in a few short paragraphs. Include what it deliberately left out.
3. **Reviewer reaction:** Nathan's own words after clicking through it, split into what worked and what didn't. The builder asks him for it in chat after deploying, then writes it down faithfully: his words, nothing added or softened, kept separate from the builder's own opinions.
4. **Builder's notes:** what's worth reusing, as mechanics, with function names; what was weak; anything noticed in the real data.
5. **Open challenge for the next demos:** what this demo didn't settle, written as prompts rather than requirements.

Order of work: build and deploy the demo, ask Nathan for his reaction, then write the whole report with that reaction in it and add the demo to the table above. The finished report is the demo's deliverable; the next demo starts only after it exists.
